# 06 · 秒杀链路白板讲稿（一张图 + 每步为什么存在 + 三层追问）

> 用法：真的在白板/纸上演示的顺序。每步都有「为什么存在」——被问「这步去掉行不行」时直接答。
> 标注约定：【实测】= 有命令可复现的证据；【推断】= 基于代码结构的分析，未压测验证。

## 0. 开场 30 秒

「我做的是旅游平台里的门票秒杀。核心问题是：2 核的小机器上，几千人抢 100 张票，怎么不超卖、
丢单、也不把 DB 打挂。我的答案是三层防线：Redis 原子扣减挡流量，MQ 异步落库削峰，
DB 乐观锁+唯一索引兜底。压测 5000 并发下超卖 0（【实测】docs/seckill-stress-report.md，
2026-11-10 真实运行）。下面我把每一步为什么存在讲清楚。」

## 2. 逐段讲：每步为什么存在（三层追问内置）

### ① 时间窗校验
- **为什么存在**：业务规则（活动没开始/已结束）；也把明显无效流量挡在最前面。
- 去掉行不行：功能上能跑（Lua 会正常拒绝），但「未开始就扣库存」是业务事故。
- 被追问：每次都查 DB 不是浪费吗？【推断】是——活动信息基本不变，可加本地/Redis 缓存，
  这是当前实现的已知优化点，我没有做（如实承认，VoucherOrderServiceImpl.java:77）。

### ② Redis Lua（核心，多留时间）
- **为什么存在**：判重→查库存→扣减三步必须原子，否则有 TOCTOU 窗口超卖。
  Redis 单线程执行一个 Lua 脚本 = 天然串行。全脚本 15 行（seckill.lua）。
- 为什么是 Lua 不是 MULTI：MULTI 不能拿中间结果做条件分支（SISMEMBER 结果决定后续走向）。
- 为什么不是分布式锁：锁要 TTL+续期，粒度错了还把所有商品串行化；Lua 按 key 天然串行。
- 【实测】5000 请求/200 库存，success=200、oversell=0、stock_after=0、errors=0，VERDICT=PASS。

### ③ MQ 异步
- **为什么存在**：把「DB 写入」从用户请求路径上摘掉——用户请求只做 Redis 判断，落库交给消费者，
  DB 按消费者的能力消化流量（削峰）。
- 为什么用户能接受异步：秒杀场景用户要的是「抢到没有」——订单号立刻返回，订单状态稍后查，
  这是电商通行做法。
- 为什么不用线程池在进程内异步：进程重启丢内存队列；MQ durable + 消息持久化，重启不丢。

### ④ 幂等查重
- **为什么存在**：MQ 至少一次投递语义 → 消息必然可能重复；不拦截就重复落库。
- 为什么订单号做幂等键：雪花 ID 全局唯一，同一订单重投被 selectById 拦截；
  「同一用户买第二次」是不同订单号，交给唯一索引，职责分离。

### ⑤ DB 乐观锁
- **为什么存在**：Redis 是预扣（可回补），DB 才是事实。`stock>0` 条件让并发 UPDATE 天然串行失败，
  是超卖的最后防线——就算 Redis 层被绕过，DB 也不会扣成负数。
- 为什么乐观锁不悲观锁：秒杀是短事务单行更新，`WHERE stock>0` 一条 SQL 就够，
  悲观锁（select for update）多一次锁等待，收益为零。

### ⑥ 唯一索引
- **为什么存在**：一人一单的最后兜底。应用层判重（Lua SISMEMBER）在 Redis 数据丢失/回补误操作时失效，
  唯一索引是 DB 层不变量，DuplicateKeyException 被捕获后回补 Redis + ack。

### 死信队列
- **为什么存在**：消费失败的消息不能无限重投（毒消息阻塞队列），也不能静默丢弃（丢单）。
  nack(requeue=false) → DLX → 人工排查后重放。
- 已知边界【如实承认】：重放路径在库存层面有二次扣减窗口（订单层面幂等），
  修复方向是消费者事务化或重放预检——docs/seckill-trace.md badcase 2 有复盘。

## 3. 瓶颈在哪（面试官问「能扛多少」时的回答框架）

| 环节 | 结论 | 依据 |
|:--|:--|:--|
| Redis 扣减 | 【实测】量级 2.7k–6.5k QPS（含隧道 RTT，仅量级参考）；瓶颈在 Redis 单线程执行脚本 | seckill-stress-report.md §3 |
| 客户端连接 | 【推断】Lettuce 单连接多路复用，高并发下命令在单连接排队，可能先于 Redis 成为瓶颈 | report §1 客户端描述 |
| MQ 落库 | 【推断】消费者单线程逐条落库，DB 单行 UPDATE 是整条链路的吞吐下限；未压测（11-11 决定暂不压测） | report §5 已知局限 |
| 时间窗校验 | 【推断】每次请求查一次 DB（VoucherOrderServiceImpl.java:77），热点读，可缓存未做 | 代码 |
| 整体 | 用户请求路径只有 ①②③，最重的 ④⑤⑥ 在消费者侧——所以「用户侧能扛、落库侧有积压时排队」是当前架构的真实形态 | 结构图 |

回答话术：「我压测过 Redis 层（数字如上），落库层没压测过，我能指出它理论上在哪——
单消费者 + 单行 UPDATE。要提吞吐就是消费者并行 + 分片，但那会引入新的幂等复杂度，
当前规模下我优先保证不丢不错，吞吐不是卖点。」

## 4. 主动承认的边界（不等人问）

1. 压测只覆盖 Redis 层，MQ 落库环节靠单测覆盖行为契约，未端到端压测（2026-11-11 决定暂不压测）。
2. 死信重放的库存窗口（§2 死信段）。
3. 时间窗校验的 DB 热点读未缓存。
4. confirm 失败的处理是「日志 + 人工」，没有本地消息表自动对账。
5. publisher-confirm 语义只保证到达 broker，不保证消费成功——消费成功靠手动 ack 闭环。

## 5. 三层追问速查表

| 环节 | 是什么 | 为什么这么选 | 换方案会怎样 |
|:--|:--|:--|:--|
| Lua | 15 行脚本原子扣减 | TOCTOU 窗口消灭于单线程 | 拆命令→超卖；MULTI→无条件分支；锁→续期复杂 |
| MQ | durable + confirm + 手动 ack | 削峰 + 不丢 | 线程池→重启丢；同步落库→DB 打挂 |
| 幂等 | 订单号 selectById + 唯一索引 | 职责分离，两级够用 | 去重表→第三级冗余；userId 幂等→混淆重试与复购 |
| 乐观锁 | WHERE stock>0 | 短事务单行，最简兜底 | 悲观锁→白等；版本号→秒杀场景无并发改写必要 |
| 死信 | DLX + 人工重放 | 毒消息不阻塞、丢单可追溯 | 无限重投→队列阻塞；直接丢弃→丢单事故 |
